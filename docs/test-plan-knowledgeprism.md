**Test Plan**

**KnowledgePrism**

**1\. Test Approach**  
Testing will focus on the MVP functionality described in the KnowledgePrism
specification. The approach combines functional, API, integration, UI,
accessibility, and data-level testing.  
The highest testing priority will be given to the core user flows:  
– Organisation Admin registration and authentication;  
– Organisation User authentication;  
– role-based access control;  
– organisation and project isolation;  
– project creation and user assignment;  
– Knowledge Base viewing and editing;  
– Add Knowledge flow;  
– Integration Preview;  
– Ask Prism semantic search and source traceability.  
Testing will be performed using risk-based prioritisation. Features related to
authentication, access control, role permissions, organisation data isolation,
and Knowledge Base data integrity will receive the highest priority, because
incorrect behaviour in these areas may expose data or allow unauthorised
access.  
Testing AI-generated output. The proposed structure in Integration Preview and
the answers produced by Ask Prism are generated by an LLM. Test cases for these
features will therefore not assert exact output text. Instead they will verify
verifiable properties: that answers are grounded in the project Knowledge Base,
that every answer carries source references resolving to real Knowledge Base
sections, that content absent from the Knowledge Base produces an explicit “not
found” response rather than an invented answer, and that the proposed structure
is derived from the existing Knowledge Base shape.  
Backlog and Post-MVP functionality – Glossary Engine, Change History, Advanced
Analysis Engine, QA Intelligence Assistant, Feedback Learning System,
Multi-Project Linking, Image Support, Monetization, and password reset – is
outside the scope of this test plan.

**2\. Functional Testing – In Scope**  
Functional testing is in scope because KnowledgePrism contains multiple user
flows, roles, permissions, and business rules explicitly defined in the
specification.  
**2.1. Landing Page**  
Testing will cover:  
– navigation from Log In and Register Organisation buttons to the corresponding
Authentication views;  
– access to the Privacy Policy view;  
– access to the Terms of Service view;  
– availability of the landing page to unauthenticated visitors.  
**2.2. Authentication and Registration**  
Testing will cover:  
– Organisation Admin registration;  
– required field validation;  
– email format validation;  
– email uniqueness within the system;  
– password strength requirements (minimum 8 characters, 1 digit, 1 special
symbol);  
– Confirm Password matching;  
– Terms and Conditions acceptance as a required condition;  
– Organisation User login;  
– invalid credentials;  
– login attempt by an inactive user (“User is inactive”);  
– login attempt by a user with no assigned projects (“User has no projects”);  
– absence of self-registration for Organisation Users;  
– successful authentication and redirection to the Organisation Workspace;  
– logout and session termination.  
This is in scope because the specification defines Authentication and Access
Control as an MVP Epic and explicitly describes validation rules and
authentication outcomes.  
**2.3. Role-Based Access Control**  
Testing will verify different behaviour for Organisation Admin, Editor, and
Viewer.  
The following permissions will be covered:  
– project visibility based on assignment;  
– access to Add Knowledge;  
– Knowledge Base editing permissions;  
– Viewer read-only access;  
– access to Ask Prism;  
– access to Organisation User Management;  
– visibility of Admin-only actions;  
– access enforcement on direct URL entry – a Viewer opening the Add Knowledge
URL, a user opening a project they are not assigned to, and an unauthenticated
user opening an internal page.  
Direct URL checks are included because hidden interface elements do not by
themselves prove that access is restricted.  
**2.4. Organisation and Project Management**  
Testing will cover:  
– project creation by Organisation Admin;  
– project deletion by Organisation Admin;  
– project visibility based on assignment;  
– user creation by Organisation Admin;  
– assignment of users to projects with Editor or Viewer roles;  
– active and inactive user statuses;  
– restrictions preventing the Admin from being deactivated or removed from
projects;  
– editing an existing user, including the optional password field.  
**2.5. User Account Settings**  
Testing will cover:  
– a non-Admin user editing their own first name, last name, and password;  
– email, role, status, and assigned projects being non-editable;  
– Settings navigation resolving to User Management for Admins and to User
Account Settings for non-Admins.  
**2.6. Knowledge Base**  
Testing will cover:  
– navigation through sections, pages, and entries;  
– opening selected Knowledge Base entries;  
– searching by title or keyword, including a search with no matches;  
– editing by Admins and Editors in the block-based editor;  
– read-only behaviour for Viewers, including the absence of the Edit button;  
– Save behaviour;  
– Cancel behaviour discarding changes.  
**2.7. Add Knowledge and Integration Preview**  
Testing will cover:  
– document upload;  
– supported PDF and TXT formats;  
– handling of unsupported file formats;  
– file size limit enforcement, including a file exceeding the limit;  
– one file per action;  
– manual text input and required input validation;  
– processing of submitted content;  
– processing errors, with retry and cancel options;  
– transition to Integration Preview;  
– proposed structure generated from the existing Knowledge Base;  
– flagging of conflicts, such as contradictory requirements or logic
inconsistencies, between new content and existing Knowledge Base entries;  
– initial Knowledge Base creation using the default template structure;  
– editing the proposed structure, including renaming and reorganising
sections;  
– adding context or decisions as new blocks in the proposed structure;  
– unapproved content not being written to the Knowledge Base;  
– approving the integration;  
– success modal;  
– Add More resetting the wizard to Step 1;  
– Go to Knowledge Base navigation.  
This is in scope because Knowledge Input and Integration Preview are explicitly
included in the MVP and represent one of the main KnowledgePrism workflows.  
**2.8. Ask Prism**  
Testing will cover:  
– submitting a natural-language question;  
– receiving a single answer;  
– retrieval of relevant Knowledge Base information;  
– an explicit “not found in the knowledge base” response when no relevant
content exists;  
– absence of speculative answers – a question on a topic outside the Knowledge
Base must not be answered from the model’s general knowledge;  
– replacing the previous answer when a new question is submitted, with no
history retained;  
– presence of source references in the answer;  
– navigation from a source reference to the corresponding Knowledge Base
section;  
– availability of Ask Prism to all roles, including Viewers.

**3\. API Testing (Postman) – In Scope**  
API testing will be performed using Postman for the main backend endpoints
supporting MVP functionality.  
API testing will cover:  
– registration;  
– login;  
– authentication and authorization;  
– project creation and management;  
– user creation and management;  
– project and role assignment;  
– Knowledge Base retrieval and editing;  
– Knowledge Input processing;  
– Integration Preview data;  
– saving approved knowledge;  
– Ask Prism queries and responses.  
API tests will verify:  
– request validation and required fields;  
– valid and invalid input;  
– authentication, including unauthenticated requests and requests with an
expired or invalid session;  
– authorization, including a Viewer calling an edit endpoint and a user calling
an endpoint for a project they are not assigned to;  
– cross-tenant requests using another organisation’s project or entry
identifiers;  
– response status codes;  
– response body structure;  
– error responses.  
API testing is in scope because the application contains role-based access and
multi-tenant data, meaning that UI testing alone is insufficient to verify
whether backend endpoints correctly enforce permissions.

**4\. Integration Testing – In Scope**  
Integration testing is in scope because several important KnowledgePrism
workflows depend on multiple system components working together.  
Authentication and Organisation Access. Verification that successful
registration creates an Organisation, an Admin account, an authenticated
session, and access to the Organisation Workspace.  
User Assignment and Project Access. Verification that a user created by an Admin
can log in, that assigned projects are available and unassigned projects are
not, and that the assigned Editor or Viewer role affects available
functionality.  
Add Knowledge Flow. Verification of the complete flow: Knowledge Input \-
Processing \- Integration Preview \- Manual Structure Adjustment \- Approval \-
Knowledge Base update.  
Ask Prism and Knowledge Base. Verification that Ask Prism retrieves only from
the selected project’s Knowledge Base, that source references lead to the
relevant Knowledge Base section, and that content added through the Add
Knowledge flow becomes retrievable by Ask Prism.

**5\. UI Testing – In Scope**  
UI testing will cover the MVP pages and their specified layouts and actions:
Landing Page, Authentication Page, Organisation Workspace, User Management
Settings, User Account Settings, Project Workspace, Knowledge Base View, Add
Knowledge View, Integration Preview, and Ask Prism View.  
UI testing will verify:  
– visibility of required interface elements;  
– role-based visibility of buttons and navigation items, including the hidden
Add Knowledge item for Viewers;  
– navigation via Organisation name according to the specified flow;  
– required fields and controls;  
– modal behaviour;  
– correct display of validation and error messages;  
– correct display of project and Knowledge Base data;  
– loading and empty states – an organisation with no projects and an empty
Knowledge Base.  
Pixel-perfect visual comparison with design files is outside the scope unless
exact visual design requirements are provided.

**6\. Accessibility Testing – Partially In Scope**  
Basic accessibility testing will be included. The following checks will be
performed:  
– keyboard navigation for primary flows;  
– visible focus for interactive elements;  
– operation of buttons and form controls using a keyboard;  
– presence of accessible labels for form fields;  
– readable error messages associated with their fields;  
– keyboard operability and focus handling in modal dialogs;  
– basic colour contrast checks where applicable.  
Basic accessibility testing is included because KnowledgePrism contains forms,
navigation, buttons, modal windows, and editable content. Full accessibility
certification and complete WCAG compliance testing are outside the scope,
because the specification does not define a required WCAG level or formal
accessibility requirements.

**7\. Data-Level Testing – In Scope**  
Data-level testing will focus on verifying data integrity and isolation for
critical MVP functionality.  
Organisation Isolation. Verification that users cannot access projects,
Knowledge Base content, or Ask Prism results belonging to another
organisation.  
Project Isolation Within an Organisation. Verification that a user assigned to
one project cannot retrieve Knowledge Base content from another project of the
same organisation, and that Ask Prism answers are grounded only in the selected
project’s Knowledge Base.  
Role and Project Assignment Data. Verification that stored user assignments and
roles match the access actually granted by the application – that a change of
role or project assignment takes effect, and that deactivating a user prevents
login.  
Knowledge Base Data Integrity.  
Verification that approved content is saved correctly, that cancelled or
unapproved content is not committed, that Knowledge Base edits are persisted,
and that content is associated with the correct project.  
Data Consistency Between UI and Backend. Verification that project data, user
roles, Knowledge Base entries, and integration results displayed in the UI
correspond to data returned by the backend.  
Direct database testing beyond validation of critical data integrity and
isolation is outside the scope unless database access is provided.

**8\. Test Environment, Tools, and Data**  
Testing will be performed on a dedicated test environment of the web
application.  
Tools: Postman for API testing; browser developer tools for UI, network, and
basic accessibility inspection.  
Test data will include at least two organisations with separate Admins, several
projects per organisation, users assigned with Editor and Viewer roles, active
and inactive users, and a set of source documents — valid PDF and TXT files, an
unsupported format, an oversized file, an empty file, and a document containing
content that contradicts existing Knowledge Base entries.

**9\. Entry and Exit Criteria**  
Entry criteria: the MVP build is deployed to the test environment; test accounts
and test data are available; acceptance criteria for the features under test are
approved.  
Exit criteria: all planned high-priority test cases are executed; no open
critical or high-severity defects remain in authentication, access control,
organisation and project isolation, or Knowledge Base data integrity; remaining
defects are documented and accepted by the team.

**10\. Risks and Assumptions**  
– Exact AI-generated output is not asserted; AI-related functionality is
verified through the requirements defined in the specification, including
grounding, source traceability, and explicit handling of missing information.  
– Quality of the extracted structure depends on the quality of the source
documents.  
– Database access may not be available, which would limit data-level
verification to what is observable through the API and UI.  
– Design files are not part of the specification, so visual verification is
limited to the layouts and elements described in it.  
– The list of supported browsers is assumed to be agreed with the team before
execution.

**11\. Out of Scope**  
– Backlog and Post-MVP features: Glossary Engine, Change History and Audit
Trail, Advanced Analysis Engine, QA Intelligence Assistant, Feedback Learning
System, Multi-Project Linking, Image Support, Monetization;  
– password reset, marked as Post-MVP;  
– concurrent Knowledge Base editing conflict handling, marked as Post-MVP;  
– user and account deletion, excluded from MVP scope;  
– full performance and load testing;  
– penetration testing and formal security audit;  
– full WCAG certification;  
– cross-browser compatibility testing beyond the agreed supported browsers;  
– mobile application testing, as a mobile application is not included in the
specified MVP scope.

**12\. Testing Priority**  
High. Authentication; authorization; role-based access control; organisation and
project isolation; Knowledge Base data integrity; Add Knowledge processing and
approval; Ask Prism grounding and source traceability.  
Medium. Validation messages; navigation; project cards and metadata; Knowledge
Base search; UI layout and role-based element visibility; empty and loading
states; basic accessibility.  
Low. Visual appearance details not defined in the specification; edge cases
without defined expected behaviour.
